## Origin

This project started as a static single-page app by Jonathan Annett (MIT licensed, copyright 2023). The original hosted at `timer.1mb.site` — a flat directory of vanilla JS and CSS files with no build step, no bundler, and no framework. It was designed to be dropped onto any static host.

The original companion app integration (for remote control via a Bitfocus product) used a file called `longPollPoster.js`. That file was experimental and the long-poll functionality was never implemented in the hosted build — it contained only `var timerAPI;`. It has since been removed and replaced with an inline declaration in `timer.html`.

## What It Does

A keyboard-driven countdown timer for presentations and conferences. Two operational modes:

- **Controller** (`timer.html`) — the operator's screen. Shows buttons, status info, and all controls.
- **Presenter** (`timer.html?presenter`) — a secondary window opened on the display screen. Shows only the countdown, colour-coded by state. No controls.
- **Shared devices** (`remote.html#…`, opened from the **share** panel's QR code) — phones, tablets and other computers as remote controls or view-only displays, plus Bitfocus Companion. See *Phone Remote Control* and *Bitfocus Companion*.

The legacy relay share (`relay.js`, `audience.html`, `relay-server.js`: room codes like `TIGER-7` over an Express WebSocket relay) was removed in Oct 2026; the **share** button now opens the pairing panel from `remote-control.js`, which superseded it.

Visual state is driven entirely by CSS classes on `<html>`. No JS touches colour or layout directly — it only adds/removes classes. This is a core architectural convention. Do not break it.

## Deployment

`public/` is a static site: copy it (and `README.md`, for the in-app help) to any HTTPS host. Its HTML pages load their scripts and styles as `name.js?v=<hash>` (first 8 hex of the file's SHA-256), written by `node tools/stamp-versions.mjs` and committed, so a changed file gets a new URL and browsers can't use a stale cached copy (the HTML itself is revalidated: the host sends `max-age=0`). **After changing any `.js`/`.css` file in `public/`, run the stamper before committing** (`--check` only reports; `tests/e2e/run_all.sh` warns when stamps are stale). Scripts loaded by script (`qrcode.min.js`, `jsQR.js`) and pages opened by script (`display.html`, `runsheet.html`, `?presenter`) aren't stamped; the vendored ones never change, and the pages are HTML, revalidated like any other. The **share** features also need the pairing server: `remote-server.js` at `wss://<timer host>:8443/` for pages from `sophtwhere.com` (and the local preview on 8444), otherwise the Cloudflare Worker at `wss://<timer host>/ws` (`RemotePeer.defaultServer()`; another server via `?remote=` or the panel's *Server* field):

```bash
npm install          # just ws
node remote-server.js --cert fullchain.pem --key privkey.pem --origin https://timer.yourdomain.com
```

`deploy/timer-remote.service` runs it under systemd (certificates via `LoadCredential`, root-only) and `deploy/certbot-deploy-hook.sh` restarts it on renewal. The hosted copy is https://timer.sophtwhere.com/beta/ with the server as the `timer-remote` service on the same VPS.

**The hosted site (timed-show.com; alpha and beta) runs on Cloudflare** from the private `timed-show-cloud` repo: a Worker serving `public/` and `README.md`, with the pairing server as Durable Objects speaking `remote-server.js`'s protocol exactly. What the code here relies on: the pairing server is `wss://<site>/ws` there (`RemotePeer.defaultServer()`; `/ws?room=<room>` or `?code=<6 digits>`, `RemotePeer.socketUrl()`, the Companion module's `socketUrl()`, the PowerPoint player); it sends no pings, so clients send `{type:'ping'}` every 25 s (`RemotePeer.keepAlive()`) and ignore the `{type:'pong'}`; the timer is served at `/` (`/timer.html` redirects there: the page opens its presenter window as `location.pathname + '?presenter'`, the manifest's `start_url` is `./`), `/o` → `overlay.html` (`overlayPage()`), `/control` → `control.html` (`controlPage()`); trial features (`pptx`) are refused there unless enabled. To run the e2e tests against it, start its `wrangler dev` (see that repo) and use `E2E_SERVER=wss://localhost:8787/ws tests/e2e/run_all.sh`.

The app requires HTTPS in production because:
- WebHID (Stream Deck) requires a secure context
- `navigator.clipboard` requires a secure context
- `screen.orientation.lock()` requires a secure context
- The original `timer.js` load guard rejects non-HTTPS unless opened as a named popup window

## The `timerAPI` Bus

This is the central integration point. **Do not bypass it.**

`var timerAPI = null` is declared inline in `timer.html` before any other scripts load. It is a plain global — not a module export.

`timer.js` and `timerapi.js` check `if (timerAPI)` before every call. When null, they run fine with no remote features.

`streamdeck.js`, `remote-control.js` and the other integrations each install themselves by wrapping the existing value:

```js
const prev = window.timerAPI;
window.timerAPI = {
  send(msg) {
    if (prev && prev.send) prev.send(msg);  // chain to previous handler
    // ... own handling
  }
};
```

This means loading order matters but they all coexist: each chains onto the one loaded before it, and every one receives every `timerAPI.send()` call.

**Outbound** (timer → integrations): `timerAPI.send({ setVariableValues: { remain, expired, impending, pausing, adjusting_up, adjusting_down, custommsg, showbar, showtimenow, showmessages, endsAt, startedAt, ... } })`

`custommsg` is the message currently on screen (`''` when none). Messages are set from several places (C key, `custommessage` command, `remote-json`, storage sync), so `timer.js` announces it from a single point: `announceCustomMessage()` runs each tick and sends only when the text changes. The `opened` command forces a resend. Don't add sends at the individual setters. On page load `timer.js` shows the stored `custom_message`, so a presenter window opened later (or a reloaded controller) shows the current message.

**Inbound** (integrations → timer): call `processTimerApiMessage({ cmd, ... })` directly. The full command set is documented in `timerapi.js`. Key commands: `start`, `pause`, `undopause`, `adjust`, `nudge`, `catchup`, `custommessage`, `settimercolors`, `keys`, `snapshot` (returns the timer state), `restore`, `runsheetnext`, `runsheetprev`, `pptxclose` (close every slide show on the PowerPoint machines so their holding slide shows; also the Stream Deck action `pptx_close`). (PowerPoint machines are only told to load, start and close decks and set the holding slide: no slide commands, by design.)

`runsheet.js` also sends `rs_active`, `rs_current`, `rs_next`, `rs_can_back`, `rs_status` and `rs_late` (seconds; + = behind) on the bus when they change. The `opened` command makes it resend.

`htmlclass` (the controller's full class list, i.e. what the presenter window copies from `remainDispClass`) is sent by `announceHtmlClass()` each tick only when it changes, and by `opened`. `video_status` (`empty`|`cued`|`playing`) and `video_name` come from the video player. `barpct` (whole percent of the progress bar) is sent by `setBarPct()` only when it changes, and by `opened`; the phone countdown display draws its bar from it. `showbar`/`showtimenow`/`showmessages` go out when toggled and on `opened`.

**Catch up:** ↑/↓ (and the `nudge` command) move `seekEndsAt`; each tick eases `endsAt` towards it by 25 ms, so the display runs fast or slow. `catchUpNow()` in `timer.js` snaps `endsAt = seekEndsAt`. It is shared by Ctrl+Enter, Ctrl+Space, the `catch up` button and the `catchup` command.

## Time Provider

**Never use `Date.now()` directly in timer logic.** Always use `timeProvider.now()` and `timeProvider.date()`.

`inettime.js` creates a global `timeProvider` that applies a cached offset between the local clock and worldtimeapi.org. This ensures the timer stays accurate if the user's system clock is wrong, and keeps two browser instances in sync across machines.

On first load with no cached offset, it fetches the internet time and reloads the page — but only if the fetch **succeeded**, the page is under 3 seconds old, no timer state exists yet, and it hasn't already reloaded this session (`sessionStorage.inettime_reloaded`). `fetchInternetTime()` returns `true`/`false`; it swallows errors, so never chain a reload on its promise without checking the result. Before v2 a failed fetch (worldtimeapi.org is flaky and often blocked by ad blockers) caused an endless reload loop.

**Script-order gotcha:** `timer.js` runs top-to-bottom and calls functions such as `getTabCount()` during startup, before later lines execute. Module-level state used by those functions must be declared with `var` (hoisted) or placed above the first call. A `let lastHeartbeat` declared next to `getTabCount()` crashed the controller on load (temporal dead zone).

## Multi-Tab Architecture

The controller uses localStorage as a simple inter-tab bus. Each tab writes its own heartbeat timestamp to `tab_<id>` once per second. `getTabCount()` scans all `tab_` keys, prunes stale ones (>3 seconds old), and returns the count.

The presenter tab (`?presenter`) does not run the timer logic (except when it's the only timer tab, e.g. while the controller reloads: it then re-reads the saved state each tick first, or it wrote back the stale end time it had read on opening and the reloaded controller's countdown jumped) — it watches for `storage` events on `remainDisp`, `remainDispClass`, and `showbar` keys and mirrors them into its own DOM. This means the presenter view works even if they are on the same machine with no network.

Shared devices (`remote-control.js`) are an additional channel on top of this, built from the same `timerAPI` bus rather than from localStorage.

## Stream Deck WebHID

`streamdeck.js` uses the browser WebHID API — no software installation required, but needs Chrome/Edge and a one-time USB permission prompt (requires user gesture).

Supported models: Mini (6 keys, 3×2), MK.II (15 keys, 5×3), XL (32 keys, 8×4).

Key images are rendered to an offscreen Canvas per key, then encoded per device generation: JPEG for gen2 (MK.2, original v2, XL), BMP for gen1 (Mini, original v1). They are sent as paged HID output reports. Only dirty keys are redrawn on each state change — not the full deck — to stay within USB bandwidth.

The in-app editor opens with the `D` key or the "deck" button. Layouts are stored in localStorage per model (`streamdeck_layout_mk2` etc.). Per-key overrides (label, fg colour, bg colour) are stored separately in `streamdeck_key_overrides`.

**Countdown keys:** the `countdown` (whole time), `countdown_major` and `countdown_minor` actions are display-only. Major/minor show `mm`/`ss` under an hour (`01` `30`), `h`/`m` from an hour up (`1h` `25m`), and a `+` prefix in overtime. They are driven by the timer's `remain` text, which is parsed into `remainSec` and deliberately kept out of `deckState`. Only countdown keys whose visible text changed are repainted (`countdownCache`), so under an hour that is one key per second. The XL default layout puts the major/minor pair at the end of row 2.

**Message keys:** the `message` action stores its text per key in `keyOverrides['<model>:<index>'].message`. Pressing shows it via the `custommessage` command, or clears it if that message is already showing. The key is lit while `currentMessage` (from `custommsg`) matches its text. `message_clear` clears any message and is lit while one is showing. The XL defaults include two message keys (`DEFAULT_OVERRIDES`) plus a clear key in row 2. The editor stops keystroke propagation from its fields so typing doesn't trigger the page-wide timer shortcuts. `applyKeyOptions()` must not call `selectKey()`, which rewrites the inputs and swallows spaces as they're typed.

**Catch up and backlight keys:** `catch_up` is drawn dim unless `deckState.adjusting_up`/`adjusting_down` is set. `brightness_cycle` steps 100 → 50 → 25 → 10% and shows the level. Brightness is a feature report: gen2 `0x03 [0x08, pct]`, gen1 `0x05 [0x55, 0xaa, 0xd1, 0x01, pct]`. It is a device setting, so it is saved immediately rather than with the layout. The XL default layout puts both keys in the empty bottom-row slots.

**Key faces:** `faceFor(model, index, actionKey)` describes a key as data (`bg`, `fg`, `big`, `wrap`, `rs`, `label`, `bar`); `DeckFace.paint()` in `deck-face.js` draws it, scaling text with the key size. `renderKey()` is just the two together. Keep look-changes in `faceFor`/`paint` so the phone's virtual deck stays identical. `window.StreamDeck` exposes `faces(model)`, `press(index, model)` and `onChange(fn)` (called after a layout save or backlight change) for it.

**Background tabs:** key repaints are scheduled with `requestAnimationFrame` only while the page is visible; hidden, they run as a microtask (`scheduleFlush()`), and a frame still pending when the tab is hidden is flushed then. Animation frames don't run at all in a background tab, so the deck used to freeze (presses still worked) unless the PiP overlay (a playing video, which exempts the page from throttling) was open. For the same reason the timer's tick (`displayUpdate`, 100 ms) comes from a tiny Blob worker (`startTicker()` in `timer.js`, setInterval fallback): background tabs slow main-thread timers to 1/s, and after a few minutes Chrome stretches chained timers to once a minute. Don't drive anything the deck, phones or Companion depend on from animation frames.

**Leaving the page** (close, reload: `pagehide`) sends the deck's reset command, one feature report without waiting (gen2 `0x03 [0x02]`, gen1 `0x0B [0x63]`), so it shows Elgato's idle screen instead of stale keys (`resetOnLeave()`; best effort, a closing page gets a moment at most; blanking every key would be far too slow; there's no whole-panel image command on these models). Confirmed on the user's deck (29 Oct 2026).

On page load, `streamdeck.js` calls `navigator.hid.getDevices()` to auto-reconnect to any previously-granted device without another permission prompt (`autoAttach()`).

**One page drives the deck:** a presenter window (`?presenter`, e.g. opened by the MK.2 default layout's *Remote* key) never attaches, and among timer tabs only the holder of the Web Lock `timer-streamdeck` does (`owner`; the lock is held until the page closes, then the next tab takes over and auto-attaches). Every page loading `timer.html` used to attach the same granted deck: both ran every press (Bar toggled twice) and both redrew all keys at once, interleaving image reports so images landed on the wrong keys (a user's MK.2: keys "moved around" after Bar). `tests/e2e/streamdeck_owner.py` checks this with a fake WebHID deck.

In the editor, **Disconnect** blanks the keys, closes the device and sets `localStorage.streamdeck_autoconnect = '0'`. That stops auto-attach on reload and replug until **Connect** is clicked, which clears the flag and re-opens the still-granted device without the picker. **Forget deck** disconnects, then calls `HIDDevice.forget()` to revoke the site's permission.

## Run Sheet

Files: `runsheet-core.js` (pure logic, shared), `runsheet.js` (controller window), `runsheet.html` + `runsheet-editor.js` (editor window). The two windows only talk through localStorage: the editor writes `runsheet` and `runsheet_cmd`; the controller is the single writer of `runsheet_state` and `runsheet_live`. Don't let the editor write `runsheet_state`.

**Sheet model:** each item has `start` (seconds since midnight, or null) and `duration` (seconds, or null). `normalise()` derives everything else. An explicit duration wins; otherwise it's the gap to the next row's start, or `perItem` minutes. The last row is the finish marker if it has a start and no duration. The sheet is *anchored* if any row has a start (planned times are clock times); otherwise planned times are offsets pinned to when the first item actually started. Starts are unwrapped past midnight. Paste/CSV detection lives in `parseText()`. Durations: a plain number is minutes, `a:b` is h:mm (same as typing into the timer), `a:b:c` is h:mm:ss.

**Next/Back:** every Next or goto pushes `{timer: processTimerApiMessage({cmd:'snapshot'}), index, currentId, finished, logLen, dayBase}` onto `state.history`, logs the actual start, then sends `default`, `start` and `custommessage` (item name). Back pops and sends `restore`, which calls `restoreTimerState()` in `timer.js` and restores the message. Snapshots hold absolute timestamps, so the restored countdown carries on as if the Next never happened. Items keep their full planned duration even when the show is late (deliberate). The current item is tracked by id, so it survives row edits.

**Reordering while running:** the editor's `moveLock(i)` returns `ran` (before the current item, or the show finished), `now` (the current item) or `next` (the item right after it, which may move down but not up); `renderStatus()` disables ↑/↓ accordingly and the click handler re-checks, so the order up to the live item never changes under the dashboard, the phones or the log. Delete an item instead.

**Ahead/behind:** for the current item, projected end = max(now, timer's end incl. pause time) compared with its planned end. Before the start it's a late start against the first planned time; after the finish it's the actual finish against the planned finish. Within ±30 s counts as on time.

**Keys:** Page Down/Up are caught in the capture phase only in run sheet mode, so outside it they still reach `timer.js` (PowerPoint mode). The editor window handles them too, so a clicker focused on it still works. **E** opens the editor (not while typing).

**Help overlay:** `help-overlay.js` (+ `help-overlay.css`) shows the README rendered by `markdown-lite.js`. It's used by the editor (**?** button, opens at *Run sheet*) and the timer page (*help* link, opens at *Quick start*). Both also open it with **?** or **F1**. On the timer page it's installed by an inline script in `timer.html` with `canOpen` = not a `?presenter` window and not `html.reduced` (P and S modes), and it closes itself if the page becomes reduced while open. While open, a window-capture keydown listener stops the page's shortcuts (so Space scrolls the help instead of restarting the timer) but lets Page Up/Down through for the clicker. It loads `README.md` next to the page if deployed, otherwise the copy on GitHub (raw.githubusercontent.com allows CORS), otherwise a link. Responses not starting with `#` are rejected, so a host's HTML 404 page isn't shown. Links to the same origin (e.g. the README's *Try it* link to the timer) are shown as plain text (`unlinkSelf()`): you're already in it, and on the phone remote it would open a second timer. Anchors use GitHub's heading slugs, so README links like `#quick-start` work in both places. `timer.css` resets all padding, so the overlay CSS sets list padding explicitly.

**Slides column:** items may carry a holding slide `holding {key, name, size}` (key `rsimg:…`, a PNG/JPG/BMP: set as the PowerPoint machines' wallpaper when the item starts) as well as `deck`; the Slides cell attaches either by file type (picker accepts both; drop on the row), shows the deck name or the image name, or two icons when both, and a small **+** for the missing one. The remote editor sends it with `kind: 'holding'`. The editor's transport bar has **Close slides** (`runsheet_cmd` `pptxclose`, remote `rs-cmd`). Items may carry `deck {key, name, size}` (key `rsdeck:<item id>:<time>`, file kept in `videoStore` like run sheet videos; `name` is the file name with its extension). The editor's **Slides** column (`renderDeckCell`, `attachDeck`; .pptx .ppsx .pptm .ppsm .ppt .pps .potx) attaches by picker or drop on the row; the remote editor sends it like a video (`rs-video` with `kind: 'deck'` → `vup-start {kind:'deck'}`; LAN only), and `remote-control.js` accepts it by file extension and stores it as `rsdeck:`. `cleanSheet()` keeps a deck only if its key is already on the sheet; `writeSheet()` and `cleanUpVideos()` remove unused `rsdeck:` blobs too. `normalise()`/`standardise()` pass `deck` through. The fixed columns nearly fill the table, so the Slides cell is compact (name truncated, full name in the tooltip) and the editor's side panel is 21 rem: check the Item column still has room after adding a column.

**Standby and auto start (Oct 2026):** `resetShow()` (run sheet mode on) calls `enterStandby()`: `default` + `start` the first item's `eff`, `pause` 60 ms later, `custommessage` its name, and the `standby` API command `{on, at}` (timer.js `setStandby()`: `html.standby`, `localStorage.standby` `{at}`, bus `standby`/`standby_at`; any `restartTimer` ends it). The notice (`#remain_info_message`, CSS `html.standby.paused`: no "Paused (for" wrapper, shown even with a message up) is `standbyText()`: *Standing by.* or *Standing by to start in m:ss…* while `at` is ahead. On the operator's screen (`:not(.reduced)`) that big notice is hidden and the dashboard's `#rs_standby` line shows it (from `snapshot.standbyText`), the times read *will start at* / *will end at* (`standby.start`, the first item's start still ahead, else now; steady, no pause total). In standby, `onKey_Pause` (Resume, from anywhere) and `onKey_Space` call `standbyStart()` → `window.runsheet.standbyStart()` = `next()`. `state.standby`/`state.autostart` live in `runsheet_state` (Reset keeps `autostart`); **Auto start at hh:mm** (`#rs_auto` on the dashboard, `#autostart` in the editor via `runsheet_live` `auto`/`autoAt`, command `autostart {on}`, remote `rs-cmd`) shows only before the show with an anchored first start still ahead (`autostartOffer()`). `standbyTick()` (worker, 500 ms) arms while counting down to the first start and fires `next()` once when it's reached (never late, not again after Back), keeps the timer's `at` in step with sheet edits, and drops `state.standby` if the timer was started some other way (`snapshot.standby`). Back to before the show restores standby. Run sheet mode off ends it (a plain pause). **Hard starts:** items carry `auto` (the editor's tick before the start, `input.hard`, on every item but the finish; ticking one without a typed start writes the start it shows as typed, to the second (`secOfDay(plannedMs(planned))`; on a sheet without times, once the show is under way, row 0 is pinned too so nothing moves), so it's disabled while there's no clock time (`provisional()`); unticking keeps the start; kept by `normalise`/`standardise`/`cleanSheet`). The first item's `auto` *is* the auto start (`firstAuto()`; the dashboard and editor-header boxes call `setAutostart()`, which writes the sheet; an old `state.autostart` is migrated on load). During the show `hardStartTick()` (same worker tick) arms each upcoming `auto` item with a typed start (anchored sheet) while counting down to it and fires once: `next()` if it's the next item, else the id goes into `hardMiss` (`runsheet_live.hardMiss` → editor `tr.hardmiss`, a red flash; dashboard status `⚠ … was due at hh:mm`) until it starts. `shiftStarts()` stops at an `auto` row with a start (it doesn't move, nor anything after it). Editor ticks are `.idle` (dimmed) unless they can fire: the first item before the show, later items once it's under way. Run sheet mode also hides the button bar's presets (`.btn-presets`, `display: contents` outside it; in it a flex box whose buttons are `visibility: hidden`, so Live adjust and the rest stay put, with the site's host name (`data-site` = `location.hostname`, set by an inline script in `timer.html`) faint in the gap from `::after`). Devices get it in the clock anchor (`s`, `sa`: `remote-clock.js` → `standby` text: phone substate, desktop display `info`, overlay strip `OverlayView.stripText()`); the timer's own overlay and Companion get `standby_text` on the bus. The presenter window now mirrors the notice (`localStorage.remainInfo`: *Paused* / standby text), which it never showed beside a controller before. Test: `tests/e2e/runsheet_standby.py`.

**Editor countdown bar:** the header ends with the time of day (`#tod`, `hh:mm:ss` from `editorNow()`, ticked on the second boundary; dim, so it doesn't compete with the countdown). The editor's header shows the timer's countdown (`#clock`: classes `impending`/`over`/`paused`/`stale`), **Pause** (`runsheet_cmd` `pause`, the toggle) and **Restart** (`restart`; one click, or two within 2 s when the editor's *Options* panel has **Restart needs a second click** on: `localStorage.runsheet_restart_confirm`, a per-computer preference that the remote editor keeps in its own computer's storage too, the one key it touches). Locally the countdown comes from `remainDisp`/`remainDispClass` (as the presenter window reads them) and goes `stale` when `runsheet_alive` stops; in `REMOTE` mode `remote-phone.js` posts `rs-clock {remain, over, impending, paused}` from its timer state on every render, and `rsCommand` in `remote-control.js` maps `pause`/`restart`. `restartCountdown()` in `runsheet.js` (`window.runsheet.restart`) sends `start` with the current item's `eff` (run sheet on, not finished) and moves that item's log entry `actual` to now (`orig` keeps the first value, `restarts` counts; `plannedMs()` in both files pins an unanchored sheet to the first entry's `orig ?? actual`, so a restart of the first item shows as late instead of moving the plan), else `start` with the default; no message, video or slides.

**Actual and expected times:** once an item is running, the editor's Start/Ends cells show what happened and what's expected (display only; the sheet keeps only typed values): started rows (`rowRole` `done`/`now`) show the log's `actual` start to the second (`clockSec`; Restart and ▶ move it) and, when finished, the next log entry as their end; the live row ends at `max(live.curEnd, now)`; the rows after it come from `RunsheetCore.project(norm, cur, endMs, plannedMs)`: each follows on from the one before, a row with its own `start` waits for it if that's later (a gap), `.finish` is the show's end. A row whose own start is what it waits for (or a knowingly saved clash) shows its typed value, otherwise the estimate as the placeholder; the Status column shows *planned hh:mm* when the estimate differs. `runsheet.js projections()` does the same from the timer's own end (`max(now, timerEndMs)`) for the dashboard's Next row, `rs_list` (`x`, `xe` = earlier than planned; the phone colours them) and *finish ≈*. End times typed for future rows count from the estimate shown (`projNow()` in `endToDuration`). `renderStatus` never rewrites the focused or an invalid input. While paused, `statusInfo()` prefixes *Paused m:ss* and the times tick up each second.

**Editing during the show:** `rowRole(i)` in the editor: `done` (in the log and before the live item, or the show finished), `now`, `next` (first non-hidden row after the live one, finish marker included). `done` rows and the live item's start are `readOnly` (`tr.locked`; video/slides buttons disabled, drops ignored); the change handler re-checks. ✕ on a `done` row sets `hidden: true` (kept by `normalise`/`standardise`/`cleanSheet`, so planned times don't move; not shown in the editor unless *Show deleted*, not in `rs_list`, skipped by `nextIndex`/`goTo`; Back onto one unhides it; `resetShow()` drops them; Replace/Clear sheet keep completed rows as hidden; Clear sheet is in the Add items panel and above the ✕ column, `#clear-all-head`, both `clearSheet()`). Changes to the live item go to `runsheet.js` as commands, which change the sheet and the timer together (`runsheet.js` now writes `runsheet` too, via `writeSheet()`): `livename {id, name}` (after the editor's `ask()` dialog; replaces the message only if it's the item's name; updates the log entry's name), `curdur {id, duration}` (refused when the timer would already be over; `adjust`s the timer by new − allotted and shifts later rows' explicit starts by new − eff), `curend {id, endClock, nextId?}` (a time of day, turned into a timestamp on the timer's own clock by `clockToMs`; with `nextId` it's the next item's new start and the rows after the next one shift by its change, without it (the live item's Ends field) the rows after the live one shift). Ripples use `RunsheetCore.shiftStarts(sheet, i, delta, to?)` (explicit starts after row i, not hidden, up to row `to` if given) and `dayDelta()`. An end typed for an upcoming row becomes a duration in the editor's `endToDuration()`, measured from the start **as the row shows it** (`plannedMs()`, seconds dropped like `clockOf`), so it works for unanchored sheets (pinned to the show's first start, which has seconds) and "10 minutes later" is exactly 10 minutes; before the show starts an unanchored sheet has no clock times, so it asks for a duration instead. Typed times go through `readClock()` (the import's `parseClock` plus `930`/`1815`; not added to `parseClock` itself, so CSV column detection is unchanged). Refused values get a dialog (`refuse()`) and stay red with the reason as the tooltip. Every duration or end edit of an unfinished row ripples (the editor's `setDuration()`; clearing a duration doesn't), as does a next-start edit with either answer and any other start edit (`setStart()`: by the change from the row's planned start, typed or derived; not when cleared or on an unanchored sheet). The **Ends** column is an `input[data-field=end]` whose placeholder is the worked-out end (never stored): typing one sets the duration (`liveEnd()` for the live item). The editor checks first: duration against the preview's remaining time, next start against `editorNow()` and `live.curEnd`. `syncFromTimer()` (every second) turns time changed on the timer into the live item's duration (+ the same shift): allotted = `seekEndsAt − startedAt − pauseAcum` (pauses don't change it), only while `startedAt === state.timerStart` (set by `startItem`/`restartCountdown`/Back), not for video items, after two equal readings. `runsheet_live` carries `curId`/`curEnd` (the timer's end incl. the pause so far); the editor marks the next row's start `.conflict` when it's before `curEnd`. Remote: `rsCommand` validates `curdur`/`curend`/`livename`; `remote-phone.js` relays `duration`, `end`, `nextStart`, `nextId`, `name`. `ask(html, buttons)` is the editor's own dialog (three-way choices; Escape = the cancel button; stops Page Up/Down while open).

**Provisional times:** an unanchored sheet before its first Next (`provisional()` in the editor: no log entry but `end`, not finished) has no clock times, so the editor's `plannedMs()` counts from `editorNow()` (pinned to the first non-hidden row) and the transport line says *times as if it started now*; a 5 s interval re-renders the status meanwhile. End times typed then work from those starts. `runsheet.js` has `provisionalMs()` for display only: `scheduleList()` (`rs_list` `p`) and the *Ready* status (*finish ≈ … if started now*); `lateness()` and the log never use it.

**Scaling a selection:** clicking a row's number (`td.num`, `pickRow()`, Shift = range) selects rows that `canPick()` (not done/now/hidden/the finish/video items); `prunePicked()` drops rows the show reached (renderAll, and renderStatus first). With 2+ picked, the `#scalebar` slider (`scalePct`, 50–150 %) previews: `renderAll()` normalises the real sheet, then if `previewing()` sets `view = scaledCopy(norm)` and `norm = normalise(view)`; `renderTable`/`renderStatus` read rows from `view` (it is the sheet itself when not scaling). `scaling` makes the table read-only (inputs, ↑/↓, ✕, media; ▶ and Next/Back still work). `scaleInto(target, n, pct)` sets each picked row's `duration` to `scaledDur(eff)` (15 s steps, exact at 100 %) and `shiftStarts(..., d − eff, lastPicked)`: starts move within the selection, rows after it keep theirs (the target). `scaleFacts(pct)` gives the bar's total, the last picked row's end (projected via `projNow(n)` while live, else planned) and the row after it with its target (`plannedMs` on the real sheet); `fitPct()` binary-searches the largest pct that gets it started on time. Apply = `scaleInto(sheet)` + `saveSheet()` (so remote editors save via `rs-save`); Cancel/Esc drop the selection. `plannedMs(sec, n)`/`projNow(n)` take the normalised sheet to use.

**Editor sizing:** `runsheet.html` sizes everything in `rem` from `html { font-size: 1.27vw }` (width-based, so the table keeps its proportions), like the timer page's viewport units. Chrome zooms per site, and people zoom the timer window to size its buttons, so the editor must not use `px` (except 1px borders) or it would scale along with them.

**Layout:** on the controller in run sheet mode the dashboard takes the top-left half and the controller's copy of the message moves to the top right (`html.runsheet:not(.reduced) #custom_message`). The presenter view is unchanged.

**Tests:** `runsheet-core.js` exports via `module.exports` when loaded in node. The pure functions are easy to unit-test there.

## Phone Remote Control (experimental)

Opened by the **share** button (`#btnshare`; the panel element is still `#phone-panel`, and the button reads `share ·` when on, `share N` with N devices). Pieces: `remote-server.js` (standalone pairing server, wss on 8443, TLS from `--cert/--key` or systemd `$CREDENTIALS_DIRECTORY`), `remote-control.js` (timer), `remote.html` + `remote-phone.js` (phone), `remote-peer.js` (shared).

**Pairing:** the timer makes a room code and four 24-char keys: control, view-only, admin and companion (`remote_pairing`: `key`, `view`, `admin`, `comp`). A control link is `remote.html#r=<room>&k=<key>[&s=<server>]`; a view-only link is `#r=<room>&v=<view key>&m=<countdown|runsheet>[&s=…]`; an admin link is `#r=<room>&a=<admin key>[&s=…]`; a PowerPoint link is `pptx.html#r=<room>&p=<pptx key>[&s=…]` (to copy; see *PowerPoint machines*); a Companion link is `#r=<room>&c=<companion key>[&s=…]` (shown as text to copy, not a QR code; `remote.html` treats `c` as a control link if someone opens it anyway). Each carries only its own key. The panel's mode selector (`remote_link_mode`) picks which the QR code shows. The link's fragment never reaches the web server. `s` is omitted when it's the default `wss://<host>:8443/` (the phone derives it), keeping the QR code small. Old `server/room/key` names are still accepted. The QR code is drawn by `qrCanvas()` from the qrcodejs model (`_oQRCode`) on whole device pixels with a 4-module quiet zone; clicking it shows a full-screen version. The panel's CSS is injected by `remote-control.js` (`PANEL_CSS`), not kept in `timer.css`, so a browser with a stale cached `timer.css` can't show it unstyled underneath the button bar. The panel sits below the bar (`--buttons-bottom`), is 440 px wide (all six link buttons on one line; never wider than the window) and shrinks the QR on short windows. The server stores only a SHA-256 of the key, rejects joins with the wrong key, and won't let another key take over a room. It checks `Origin` against `--origin`. Limits: 16 KB per message, 40 messages/s per socket, 16 phones per room. Rooms survive a timer reconnect for 2 minutes. Every socket has an `error` handler; without it an oversized frame crashed the whole server.

**Server protocol** (the server never inspects payloads): host `{type:'host',room,key,viewKey,adminKey,compKey}` → `hosted{room,protocol}` (`PROTOCOL` 2 = view-only keys, 3 = admin keys, 4 = companion keys, 5 = PowerPoint keys (`pptxKey`, role `pptx`), 6 = pairing codes (see *Pairing by code*); older servers send none. `MIN_PROTOCOL` in `remote-control.js` says what each link needs; the timer warns in the panel and refuses shares the server can't serve, since an old server rejects unknown keys as `not-found`); phone `{type:'join',room,key}` → `joined{id,hostOnline,role}`, and the host gets `peer-join{id,role}`. The role is `admin`, `companion`, `pptx`, `control` or `view` by which key the phone used (the server stores only hashes). A host re-registering with a different view, admin or companion key drops the phones using the old one. Then host `{type:'to',id,msg}` ↔ phone `down{msg}`, phone `{type:'up',msg}` ↔ host `from{id,msg}`. Also `peer-leave`, `host-offline` and `host-online`; on `host-online` the phone starts a fresh link.

**Proximity check (always on; replaced the opt-in *Require a PIN* in Oct 2026):** every peer starts `approved: false`. An unapproved peer gets `{t:'pin-required'}` in answer to `hello` (unless the hello carries a `token` in `remote_approved`), nothing is pushed to it and nothing else from it is acted on (checked before the role gate, the `ALLOWED` map, everything). The device makes a **3-digit** number (Companion and the PowerPoint player too; the timer accepts 3 or 4 digits from older ones), shows it at a moderate size (readable at arm's length, not across a room: phone 1.9em, overlay 26 px, receiver 30 px) and sends `{t:'pin', code}`; the timer lists it in `.pp-pending` (and opens the panel); someone near the device (or on the phone to them) types it. `approvePeer()` compares, issues a 24-char token (`{t:'pin-ok', token}`, kept by the device as `remote_token_<room>` / `overlay_token_<room>` / `pptx_token_<room>` and sent with every hello). **One wrong number** → `rejectPeer()`: `{t:'pin-rejected'}`, peer ignored, and 400 ms later `{type:'kick', id}` makes the server close its socket (server sends it `error rejected`, the host `peer-leave`); devices don't reconnect after either (`fatal`/`refused`; Companion stays `rejected`). Code pairing grants no token, so a paired overlay passes the check like any device. **The panel closes itself** (`panelConnected()`, also the full-screen code) when an approved phone says hello, unless a request is pending, so the code isn't left on screen. `pairing(true)` (New code) clears `remote_approved`. The phone reloads on `hashchange` (a rescan in the same tab). A phone dropped by the timer (`pin-rejected`, `revoked`) shows why for 2.5 s, then forgets its link and token and goes to `control.html?left=revoked|refused` (`toCodeScreen()`; `?remote=` kept when not the default); **Unpair this device** goes there too (`left=unpaired`), and so does `remote.html` opened with no link. On the touch timer, the ⋯ item becomes **Take back control** while `remoteControl.shared` (sharing on with a device connected or approved): `takeBack()` tells and kicks every device, clears the approvals, then `pairing(true)` + `disable()`; the item then says it's done. **Devices:** the `pin` message carries the device's suggested name (`RemotePeer.deviceName()`: "iPhone · Safari"; the overlay, receiver, Companion and PowerPoint player prefix or use their own), kept as `e.suggest`, then as the approved entry's `name`; a returning token restores `e.token`/`e.name` and updates `seen`. The panel's `.pp-peers` lists each device (`.pp-dev`: `deviceLabel()`, role, link) with **Rename** (`renameDevice()`, a prompt) and **Revoke** (two clicks within 3 s, `armedRevoke`; `revokeDevice()` removes the entry, sends `{t:'revoked'}` and kicks it; devices treat it like `pin-rejected`), and below them `.pp-known` (a `<details>`) lists approved devices not connected, with the same buttons. `.pp-pending` is rebuilt only when the waiting requests change (`dataset.sig`; a rebuild lost focus mid-typing); a new request or the panel opening puts the caret in the first empty box (touch too) unless another field is being typed in. `control.html` and the overlay's code box refocus on window focus and on a tap/click elsewhere. Tests type the numbers with `tests/e2e/_proximity.py approve(t)` (run_all.sh skips `_*.py`).

**Link (`remote-peer.js`):** a WebRTC data channel with public STUN (`stun.cloudflare.com`, Google's) and **no TURN**, so it connects directly on the LAN and, when the routers allow it, across networks. `route()` reads the selected candidate pair once the channel opens: `mode` `'lan'` when neither end is srflx/relay or a public IPv4 address, else `'p2p'`; only `'lan'` allows file transfers (videos, decks: the existing `mode !== 'lan'` checks). **Retry:** a device in server mode sends `{t:'relink'}` (phone badge tap, overlay status click, receiver badge, `RemotePeer.retryOnNetworkChange()`: `online` and `navigator.connection` change); the timer (any approved role, at most every 5 s) calls `peer.restart()`, which makes a new offer; the non-initiator accepts a new offer with a fresh connection. A websocket reconnect already gets a fresh attempt (a rejoin is a new peer). The timer is the initiator. Payloads are `{k:'sig', sdp|ice}` for signalling and `{k:'data', d}` for fallback data, both via the server. It gives up after 7 s or when the connection fails/closes, and `send()` then uses the server. It works with browsers' default mDNS-hidden host candidates. `onMessage(obj, via)` says which path a message came by (`'lan'` or `'server'`). Binary messages (`sendBinary`, `onBinary`, `drained(bytes)` for backpressure) exist only on the data channel. `RemotePeer.sendBig(peer, obj)` splits big JSON into `{t:'part', pid, i, n, s}` messages of ≤3000 chars (the server's 16 KB limit, after escaping), paced at 80 ms through the server (it drops over 40 msgs/s per socket); `RemotePeer.joiner()` reassembles them.

**Countdown anchors (Oct 2026):** a device that says `{t:'hello', clock: 1}` (phone, overlay; `e.clock`) isn't sent `remain`/`over`/`impending`/`pct` (`CLOCK_FIELDS`), which change every second; it gets `clk` instead: `{r, e, d, rr, er, f, p, a}` from `timer.js announceClock()` (remaining/elapsed ms with their rates: −1 running, 0 paused, −1.25/−0.75 while easing; total; before-start and paused flags; `a` = its age as it leaves, `pushTo`), sent only when the last anchor's prediction is >150 ms off or a flag changes (`opened` forces one). `remote-clock.js` (`RemoteClock.create(onChange)`, worker-ticked so it runs minimized) counts from arrival and formats with timer.js's `secToStr` rules, so a running or easing countdown sends nothing (rooms can hibernate). Older devices still get the per-second fields and no `clk`; a new device on an older timer gets no `clk` and uses them. Still per second: the virtual XL's countdown keys and run sheet `rs_late` when late, and Companion's variables. ## Bitfocus Companion

`companion/companion-module-sophtwhere-presentationtimer/` is a Companion connection module (`@companion-module/base` 2.0, ESM, TypeScript, Node 22; `npm install && npm run build`, `npm test`, `npm run package` → `.tgz`). It is the one part of the repo with a build step, by necessity; it's an independent npm project, nothing in `public/` depends on it. Companion loads it from a *developer modules path* pointing at `companion/` (each module in its own folder with `companion/manifest.json`, entrypoint `../dist/main.js`), or from the packaged `.tgz`.

**Timer side (`remote-control.js`):** a peer joining with the companion key has role `companion`. In `onPhoneMessage`, after `hello`, `{t:'api', req, msg}` from a companion peer goes to `apiFromCompanion()`: `msg` must be an object with a string `cmd` not in `API_DENY` (`redirect`), and is passed to `processTimerApiMessage` whole; the reply is `{t:'api-result', req, result}` or `{…, error: 'bad'|'refused'|'no-timer'|'failed', detail}`. Companion peers also get the `control` handling (`ALLOWED` map, deck, keys) and the raw bus: `installBus` records every primitive `setVariableValues` value in `rawVars`, and `pushVars(e, full)` sends `{t:'vars', full, v}` diffs per peer (`e.varsSent`, reset by `hello`) from `pushTo`. They are not admins (no `share`). `MIN_PROTOCOL.companion = 4`: an older server would reject the key as `not-found`. The PIN flow applies unchanged (the pending row says *Companion wants to connect*; the module shows its PIN in its status and log and keeps the token in its config).

**Module (`src/`):** `link.ts` — `parseLink()` (whole URL or fragment; `c`/`a`/`k`/`v` keys; derives `wss://<host>:8443/` when `s` is absent) and `TimerLink`, a plain `ws` client of the pairing server (join → hello → `state`/`vars`/`api-result`; ignores `{k:'sig'}` so the timer falls back to the server after 7 s; `not-found`/`room-closed` retry every 15 s; `api(msg)` with request ids and a 5 s timeout; PIN: random 4-digit code, `pin-ok` token event). `main.ts` — `InstanceBase` subclass (default export, as base 2.0 wants; no `runEntrypoint`): maps link status to `InstanceStatus`, batches `vars` diffs over 40 ms into `setVariableValues` (booleans as `'true'`/`'false'`, null as `''`) and `checkFeedbacks(...FEEDBACK_IDS)`, adds variable definitions for unknown names as they arrive. `actions.ts` — every API command as an action (`parseDuration()`: minutes, h:mm, h:mm:ss, `90s`, `20 min`, `1 h`); option values arrive with variables already resolved (base 2.0 has no `parseVariablesInString`). `feedbacks.ts` — boolean feedbacks over `link.vars`; `FEEDBACK_IDS` must list them all. `presets.ts` — `type:'simple'` presets with a `CompanionPresetSection[]` structure built from categories. `variables.ts` — `KNOWN_VARIABLES` (keyed object). `src/__tests__/defs.test.ts` cross-checks presets against the action/feedback definitions. `companion/HELP.md` is the user guide shown in Companion. The end-to-end test `tests/e2e/companion_link.py` (+ `comp_link.mjs`) drives `dist/link.js` against a local pairing server and a Playwright timer page; use that rather than testing inside Companion.

**Not done yet:** a local-only mode (the module hosting the pairing server/serving `public/` itself for users without a server), a WebRTC LAN link (not needed: a few hundred bytes a second), key-face image feedbacks (`deck-face.js` as PNG for Companion buttons), submission to Companion's module store.

## Video player

`dropPlayer.js` writes a player page into a named pop-up (`video_player_window`, opened by the **video** button (in `video-library.js`) or on demand during a key press; browsers block it otherwise) and drives its two `<video>` elements from the timer window: a **playing** slot and a **cued** slot (loaded, paused at 0), so the next video can load behind one that's playing. `arrange()` shows the playing one on top, otherwise the cued one (opacity 1, or 0 for "black"). Everything goes through `window.videoPlayer`: `open()`, `isOpen()`, `load(url, {name, idle, controls, message, revoke, tag, onEnd, history})` cues, `loadFile(file, handle)` cues a dropped/browsed file, `play()` plays the cued video and starts the timer (`start` with the clip's whole seconds, message `Video: <name>` unless `message`), `stop({quiet})` unloads the playing video (else the cued one) and, unless quiet, clears message and timer, `rewind()` re-cues the playing video at 0 with the timer paused at its length (pause sent 60 ms after the start: paused at exactly N.000 s the display reads N+1), `unloadCued()`, `setIdle()`. `onEnd: 'unload'` (drops) stops and clears; `'recue'` (run sheet) goes back to before-play, timer 0:00, message kept. `state()`/`onChange(fn)` report `{status, name, idle, duration, playing:{tag,name}, cued:{tag,name,idle}}`; it also publishes `video_status`/`video_name` on the bus. API commands `videoplay`/`videostop`/`videorewind` call it. A `NotAllowedError` from `play()` (autoplay with sound) shows a toast asking for a click in the player window. On-screen controls (`#video-controls`, styles injected): all of them for `controls: true` loads (drops); for run sheet videos only ⟲/■ while playing and ▶/■ once `rewound` (set by `rewind()` and the `recue` end, cleared by `play()`), never for a preloaded next item (it would play out of turn). The label is the message (`messageFor`). The player page must not load external scripts (written with `document.write`; an external `<script src>` stalled the parser so nothing after it ran); it forwards keys to the timer with `postMessage` to `window.opener.location.origin` (its own `location` is about:blank). `localStorage.video_idle` holds the drop default.

**Video panel and Recent videos (`video-library.js`):** the **video** button opens the player window (needs the click) and toggles `#video-panel` (CSS injected; under the button bar like the phone panel; the two close each other via the `timer-panel` document event). *Browse* uses `showOpenFilePicker` (keeps the handle) or a hidden file input, opening the player during the click first. Loads carry a `history` descriptor (`{kind:'file', file, handle}`, `{kind:'link', url}` for http(s) links only, `{kind:'runsheet', key}`, `{kind:'recall', id}`); `dropPlayer.play()` calls `videoLibrary.played()` when the video starts, which dedupes (file name + size, url, store key) and returns the entry id, and the slot's history becomes `recall` so a rewound replay counts on the same entry. Drops ask `DataTransferItem.getAsFileSystemHandle()` during the drop event. A file is kept as its handle in `videoStore` under `vhist:<id>` (Chrome/Edge; `recall()` calls `queryPermission`/`requestPermission`, which needs the click), else as a copy within `COPY_LIMIT` and 80 % of the storage quota, else `stored: 'none'`. Run sheet entries point at the `rsvideo:` blob; the editor's `cleanUpVideos()` keeps keys listed in `video_history`, and dropping such an entry deletes the blob only if the sheet no longer uses it.

**Run sheet videos:** items may carry `video {key, name, size, duration}` and `videoIdle` (`show`|`hide`); `normalise()`/`standardise()` pass them through. The editor's Video column attaches a file (picker or drop on the row): `probeDuration()`, then `videoStore.put('rsvideo:<id>:<time>', file)`; the item's duration (if empty) and name (if empty) come from the video. Unused `rsvideo:` blobs are removed 3 s after the editor opens and when a row is deleted. In `runsheet.js`, `startItem()` calls `playItemVideo()` for a video item (plays the cued video if its `tag` is the item id, else fetches, cues and plays; `pendingPlay` holds `preloadNext()` meanwhile so the next preload can't take its place) and `stopRunsheetVideo()` otherwise; `back()` stops it too. `commit()` calls `preloadNext()`, which cues the next item's video (or unloads a run sheet video no longer next) but never replaces a dropped video's cue. Deck actions `video_play`/`video_stop`/`video_rewind` are lit from `deckState.video_cued`/`video_playing` (derived from `video_status`).

## PowerPoint machines (experimental)

**Alpha-only trial (Oct 2026; the user hasn't decided whether to keep it, partly because a PowerShell script may look like an attack vector):** `features.js` (loaded first by timer, editor, phone and receiver pages) sets `TimerFeatures.pptx` true only on `alpha.*` hosts and localhost (tests set `window.TimerFeatures` first). Off, `html.no-pptx` hides the editor's Slides column and Close slides, the share panel's PowerPoint button and the admin phone's PowerPoint option; `pptx-hub.js` doesn't install (`window.pptxHub` absent, so `runsheet.js`/`timerapi.js` do nothing), the deck palette leaves out `pptx_close` (`action.pptx`), `remote-control.js` doesn't send `pptxKey` and refuses deck/holding uploads, the editor ignores dropped decks, and `pptx.html` says it isn't available. The Worker enforces it as well: without `pptx` in its `FEATURES` var it 404s `pptx.html`, `pptx-receiver.js` and the `.ps1`, and the Room ignores `pptxKey` (so PowerPoint joins get `not-found`). Test: `tests/e2e/features_pptx.py`. User-facing docs moved from the README (the in-app help) to `docs/powerpoint.md`.

Setup, behaviour and the full protocol are in `docs/powerpoint.md`; read it before changing anything here. Summary: a PowerPoint machine is two peers joined with the PowerPoint key (role `pptx`): the receiver page `pptx.html` (saves decks into a folder chosen with `showDirectoryPicker`, handle kept in IndexedDB `pptx-receiver`) and the player `Pptx-WsController.ps1` (PowerShell 5.1/7, speaks the pairing-server protocol like the Companion module, starts decks with `powerpnt /S` and works the show window; **no COM**, which caused trouble closing files). They are paired by the id the receiver writes into `<inbox>\.timer-pair` and the player reports (`hello.pair`, verb `check`).

**Timer side (`pptx-hub.js`, `window.pptxHub`):** `remote-control.js` hands it every `pptx` peer (`join`, `leave`, `message` for `hello`/`pp-*`/`pf-*`, `mode`) and nothing else: these peers get no timer state (`pushTo` returns early) and their messages never reach the `ALLOWED` map or the API. The PIN gate applies before the hub sees anything. Machines are keyed by pair id; a player whose inbox id matches no connected receiver sits in `loose` (re-checked when a receiver says hello). `sync(M)` walks `deckList()` (current item's deck, next, the rest after, then before): sends missing decks to the receiver (`transfer`: `pf-offer`, then 64 KB binary pieces with a 4-byte transfer number, at most 16 MB unacknowledged, LAN only, files read from `videoStore`), then `send` to the player (copy Inbox → Show; the ack's `result` is the name to `start`), and `tidy` once all are in. Player commands are strictly one at a time (`cmd`/`pump`, ack by `req`). `start(item)` (from `runsheet.js startItem`) sets the item's holding slide as every machine's wallpaper (`holdingOn`, `pendingHolding` until it's there) and starts its deck on every machine, or marks `pendingStart` until it's ready. **Only user actions open or close anything** (Next, Back, Close slides): a player connecting or reconnecting gets no `start`/`wallpaper`/`stop` (`attachPlayer` clears the pending ones; nothing is queued for a machine whose player isn't connected; `leave` clears them), the timer page reloading likewise; pending ones apply only while the deck is still being prepared for a connected player; `close()` sends `stop all` everywhere and clears `pptx_last`; `current(item)` (from `back`) re-starts an item's deck if another is up; items without a deck do nothing (the last deck stays up). `changed()` is called from `runsheet.js commit()`. Inbox file names come from `fileName(deck)`: `<name> ~<tag>.<ext>`. `summary()`/`describe()` feed the share panel (one line per machine), `hint()` the dashboard status, `infoAll()` the receiver pages, `announce()` the bus (`pptx_machines`, `pptx_current`, `pptx_showing`, `pptx_next_ready`; resent on `opened`).

**Receiver (`pptx-receiver.js`):** checks every offer (key format, plain PowerPoint file name, size ≤ 8 GB, LAN, folder chosen), writes with `createWritable()` (the browser swaps the file in on `close()`, so the player never sees half a deck), reports `pf-prog` every 2 MB, keeps its own index (`pptx_receiver_files_<room>`, checked against the folder on load) and only ever deletes files it saved (`pf-tidy`). Other keys: `pptx_saved_link`, `pptx_receiver_id`, `pptx_token_<room>`, `pptx_presenter` (the Presenter View box: adds `-NoPresenterView` to the command), `pptx_rehearsal` (the Rehearsal box). It shows the exact player command with the full link.

**Player script:** keeps one `ReceiveAsync` pending and polls it (`Wait(200)`), so the server's 25 s pings are answered while a copy runs (copies run in a background runspace; `KeepAliveInterval` 10 s as well). **No PowerPoint COM** (the user found it caused problems closing files): `start` runs `powerpnt.exe /S <file>`, waits for the deck's show window (user32 via an `Add-Type` class `TimerWin`: windows of `POWERPNT` with class `screenClass`/`PodiumParent` and the deck's name in the title), starts every deck from a clean slate (`Start-Show`; the user's call after seamless switching proved fragile): (1) `Clear-Shows`: `WM_CLOSE` every slide show window (Esc if they linger; Presenter View goes with its show, so it's never touched), then wait for PowerPoint to finish quitting if it has no windows left (a new `/S` handed to a dying instance would be lost); (2) `powerpnt /S`, wait for the deck's show window (+ `$SettleMs`, 1 s); (3) Presenter View on with the keys (`Set-PresenterView`: focus the show (Alt tap + `SetForegroundWindow`), Menu key (VK_APPS), R, only if `Test-PvUp` says it isn't already as wanted: a `PodiumParent` window, a window titled *Presenter View*, or two show windows for the deck, looked for up to 3 s, since pressing when it's up closes it; Presenter View is the default, `-NoPresenterView`). `stop all` (Close slides) is `Clear-Shows`. **Rehearsal mode** (`$script:Edit`; verb `mode edit|show`, sent by the hub when the receiver page's *Open decks for editing* box (`pf-mode`, `hello.edit`, localStorage `pptx_rehearsal`) differs from the player's `hello.edit`; `-EditMode` to start in it): step 2 opens the deck without `/S`, waits for its `PPTFrameClass` window, focuses it and sends Esc then F5 (twice at most), and never toggles Presenter View (F5 follows PowerPoint's own setting; toggling closed the Presenter View PowerPoint had just opened); `Clear-Shows` also closes the player's own editor windows (`PPTFrameClass`, title naming a file in Show), if there are any, quits PowerPoint with Ctrl+Q (`TimerWin.CtrlKey`; Ctrl+W was tried and left PowerPoint's empty frame window, same handle, so the player waited forever) and answers the save prompt with S (300 ms after Ctrl+Q to the focused POWERPNT window, then to any new POWERPNT window or new focused one; the first test's prompt wasn't seen as a new top-level window, so it logs the focused window and child windows (`TimerWin.Foreground/Children`) after 3 s for diagnosis), waiting up to 3 min for PowerPoint to quit (PowerPoint closes after a big save finishes; the hub allows 5 min for `start`/`stop all`), and `send` keeps a Show copy newer than the Inbox one (`note: 'edited here'`). **It's a toggle**, and a deck opened while another is in Presenter View inherits it, so never press without looking. Window classes confirmed on PowerPoint (Oct 2026 test): `screenClass` (title `PowerPoint Slide Show  -  <deck>`), `PodiumParent` (`<deck> - PowerPoint Presenter View`), `PPTFrameClass` editor (`<deck> - PowerPoint`). Presenter View appears a moment after the show, so look for it for a few seconds. The player still logs the windows after each start (handy for diagnosis). Shows are found by window class + the deck's name in the title each time, never by remembered handles or processes (PowerPoint is single-instance and reuses windows). PowerPoint is never killed. It never changes slides: they're advanced on each machine (by design; the timer only loads and starts decks). `pp-state` reports when the show window disappears. It removes the downloaded-file mark (`Unblock-File`) so PowerPoint doesn't use Protected View. **It has not been run on Windows by the agent**: the timer side was tested against a Node stand-in speaking the same protocol, and the receiver with the origin-private file system standing in for a folder.

## Mobile / Touch

`touchcontrols.js` activates only when `'ontouchstart' in window` is true. It:
- Shows the `#touch-strip` (fixed bottom bar: Presets, Restart, Pause (reads *Resume* while paused and blinks with *ends at*: `html.paused #touch-pause-btn`, the same `blinker` and colours), ±1 min, **⛶** full screen (the F key; only with `html.can-fullscreen`, i.e. not iPhone), and **?**, which opens the help via `window.timerHelp`, set by the inline script in `timer.html`)
- ±1 min use the `adjust` command (a synthetic Ctrl+arrow gave ±1 s: the timer only knows Ctrl is held from a real Control keydown)
- No swipe gestures (removed: easy to trigger by accident, and the ±1 min buttons do the same)
- Handles long-press on `#clock_main` (600ms) = pause/resume
- Handles double-tap = start/restart
- Builds the preset bottom sheet on demand: built-in `PRESETS` plus `localStorage.touch_presets` (minutes; `.custom` buttons), **Other duration…** switches the sheet to a keypad (`#touch-pad`, `#touch-preset-sheet.keypad`; digits = minutes, `:` = h:mm like the keyboard; Start / Set default / Save preset), **Edit** toggles removal of custom presets. Set default uses `setDefaultDuration` + a `default` announce on the bus, like `saveEditedTime`. On short screens (`max-height: 560px`) the keypad sits beside the display/actions and the sheet scrolls.
- **⋯** opens `#touch-more-sheet`: a row of **Bar** / **Clock** (B / T, showing On/Off) and **Undo pauses** (`'`; disabled with no pause to undo: not paused and `#extra_time_disp` empty) (`moreSwitches()`); each buzzes (`vibrate(30)`), shows its new state and closes the sheet 500 ms later (`switched()`), then *Let a friend control this timer* (`window.remoteControl.open()`: the phone panel from `remote-control.js`, which on touch devices (`TOUCH`) is a bottom sheet `#phone-panel.pp-touch` offering only the control and countdown links, no run sheet/admin, server details hidden; a stored `remote_link_mode` outside those reads as `control`; sideways it's a grid with the code on the right) and *Help*. There the panel shows a **6-digit code by default** instead of the QR (`codeMode()`: touch, protocol 6, `localStorage.remote_touch_qr` not `'1'`; **Show QR code instead** / **Use a code instead**, `.pp-qrswitch`): `renderPairing()` starts pairing (`pair.kind = 'phone'`) whenever the panel is open, `grantClaim()` sends `shareFragment(linkMode())` (control or countdown), and the friend types it on `control.html` (`<host>/control` on the Worker, `controlPage()`), which opens `remote.html#…`. After a grant `pair.note` stays up (no new code) until the panel is reopened.
- Installs `BackGuard` (back-guard.js: pushes a sentinel history entry and re-arms on every `popstate`; closers are tried newest first). Its closer backs out of the keypad, closes the sheet or the quick-start overlay; `HelpOverlay.install()` registers the help's own closer when `BackGuard` exists, so load `back-guard.js` before `help-overlay.js` and `touchcontrols.js`. `remote-phone.js` does the same for the view menu, message box and full-screen tip. With nothing open, Back does nothing (deliberately not pause/resume: an accidental press shouldn't change the timer).
- Shows the quick-start overlay on first load if no timer state exists

All gestures dispatch into the existing `onDocKeyDown`/`onDocKeyUp` keyboard handlers — `touchcontrols.js` has no timer logic of its own.

On touch screens the progress bar (`.mainDiv`, 12 px) sits just above the strip, with the time details above it while `showbar` (and the pause total `#extra_time_disp` just above *total*: `7vh` over the same base; at `80% + 20px` it covered it in portrait and sat behind the strip in landscape); a phone on its side (`(pointer: coarse) and (orientation: landscape)`) gets bigger details (4.5vh values, 3.5vh labels, 7vh time of day, 14 px *messages enabled*; at the body's 2.5vh they were 10 px), still clear of the centred countdown at 1:14:58 on a 667×375 screen (at `top: 80%` it landed on the strip in landscape); in portrait (`orientation: portrait`, any screen) messages are capped by the width too (`min(10vh, 9vw)`; they wrapped over the countdown). On touch screens (`@media (pointer: coarse)` in `timer.css`) the keyboard hints (`#disp_next_mins`) and the "open timer display / help" line (`#link`) are hidden, and the elapsed/total/started/ends lines are positioned from the bottom, just above the strip.

The `#touch-strip` is hidden via CSS on non-touch devices (`@media (pointer: coarse)` controls visibility). The `div.buttons` desktop bar is hidden on touch devices via the same media query.

## Conventions to Follow

- **Window titles start with the site's host name** — `location.hostname + ' - ' + what` ("timed-show.com - Control Screen"; timer.js `siteTitle()`), set by each page's script; the static `<title>` is only the fallback (file://, before the script runs).

- **State via CSS classes** — visual state always via `setHtmlClass`/`clearHtmlClass`, never via `element.style`.
- **Time via `timeProvider`** — never `Date.now()` in timer logic.
- **Commands via `processTimerApiMessage`** — never call timer functions directly from integrations.
- **State out via `timerAPI.send`** — never read DOM or localStorage from integrations to get timer state; wait for it to be pushed.
- **No build step** — this is vanilla JS. No bundler, no transpiler, no TypeScript. Keep it that way unless explicitly decided otherwise. (The Companion module under `companion/` is the exception: Companion requires a packaged Node module, so it is TypeScript with its own `npm run build`; nothing in `public/` depends on it.)
- **localStorage as the inter-tab bus** — the presenter tab reads from storage events. If you add new display state that needs to reach the presenter tab, write it to localStorage and handle the `storage` event in the presenter tab's `onLocalStorage` handler in `timer.js`.
- **Leave Cmd shortcuts to the browser** — `onDocKeyDown` returns early when `metaKey` is held, so Cmd+R/C/V/P/1–9 etc. work normally on a Mac. Any new keyboard shortcut handler must do the same (check `!e.metaKey`); the timer's own modifier is Ctrl.
- **Custom CSS is a layer, not a copy** — the Ctrl+S editor shows `timer.css` plus the user's rules but saves only rules that differ, so `timer.css` changes still reach users with custom styles. Removing a property from a built-in rule doesn't take effect (the built-in rule still applies); override it instead. `OLD_CSS_RULES` fingerprints past built-in rules for migrating old full-copy saves; it's frozen and needn't be updated.
- **Chain `timerAPI`, never replace it** — any new integration module should wrap the existing `window.timerAPI` value, not overwrite it blindly.
